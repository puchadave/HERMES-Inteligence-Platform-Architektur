# Odysseus D3 Architecture

## Decision

Odysseus uses an edge-first 80/20 model. Ordinary public tasks are routed directly by the client to configured providers. Sensitive, evidence-bound, RAG-heavy, or specialist tasks are dispatched to the HP Xeon node with 64 GB eight-channel memory.

## Authorities

| Authority | Component | Responsibility |
|---|---|---|
| Search | SearXNG | Query interface, metasearch, search-profile selection |
| Identity | Keycloak | OIDC, roles, ORCID federation |
| Policy | Odysseus API | Deterministic data classification and dispatch |
| Queue | NATS JetStream | Specialist job transport and future worker federation |
| Knowledge | Qdrant | Local embeddings and RAG collections |
| Evidence | S3-compatible store | Original artifacts and append-oriented case exports |
| Inference | llama.cpp | Local GGUF models on the Xeon node |

## Data flow

1. A client receives the user task.
2. Deterministic policy marks public or specialist content.
3. Public tasks use the selected direct provider.
4. Specialist tasks enter SearXNG or the API under Keycloak authentication.
5. The API publishes a normalized NATS job.
6. Xeon workers process the job and return normalized results.
7. Evidence artifacts and hashes remain in local storage.

## Trust boundaries

- Browser to Traefik.
- Traefik to OAuth2 Proxy and Keycloak.
- Search tier to policy tier.
- Policy tier to NATS.
- NATS to specialist workers.
- Workers to evidence and knowledge stores.
- VPN search node has its own network namespace through Gluetun.

## Current implementation boundary

This foundation provides the authenticated search tier, policy API, queue, optional local model runtime, and documentation. Worker execution and bidirectional result streaming are the next implementation phase.
